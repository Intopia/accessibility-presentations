Playwright for accessibility testing:

Powerful but fragile

What will we cover?
  • A quick overview of Playwright
  • Strengths and weaknesses
  • Where it works best
  • A bit about axe-core

What is axe-core?

axe-core is an accessibility testing engine.

It comes with a large set of predefined accessibility rules that can check for issues with:

  • Images
  • Forms and interactive controls
  • HTML semantics
  • Use of ARIA
  • Colour contrast
  • Page titles and language

The axe-core engine can be used in different ways.

Use 1:

It powers tools such as axe DevTools and Lighthouse.

So, when you use axe DevTools to scan a page, axe-core runs inside that page.

Use 2:

It can also be run from the terminal.

This is how most devs use axe-core.

Use 3:

It can be integrated with Playwright for automated testing.

They all follow the same three steps:
  • Load axe-core into the page.
  • Run its predefined accessibility rules.
  • Report the results.

Results can be presented in a range of different ways.

Method 1:

Browser extensions like axe DevTools display results directly in the extension.

Method 2:

Results can also be displayed in the terminal.

Method 3:

Developers can also generate JSON files or HTML reports.

Good and bad

axe-core is very good at checking pages in their current state.

But it has limitations.

Limitation 1:

It can’t navigate between pages on its own.

When using axe-core from the terminal, you have to provide the URLs you want to test.

You can provide multiple URLs, and the command-line tool will check each page.

Other tools can also navigate between pages and run axe-core automatically.

Limitation 2:

More importantly, it cannot interact with pages on its own.

It cannot open an accordion to test its expanded state.

It cannot submit a form to trigger validation errors.

axe-core can check these states only if another tool triggers them.

What is Playwright?

Playwright is a browser automation and testing framework.

It can control a browser much like a person would.

Playwright and axe-core work well together.

There’s even an official package that connects the two:

@axe-core/playwright

But Playwright can also run accessibility tests without axe-core.

Playwright features

Feature 1. Navigate to pages

Playwright can open pages, follow links and even navigate through multi-page processes.

Feature 2. Interact with pages

Let's look at some accessibility testing examples.

Keyboard access
  • Go to a page.
  • Use Tab to move through focusable elements.
  • Check that expected elements receive focus.
  • Check that they can be activated using the keyboard.
  • Fail based on any of the above.
Accordions
  • Go to a set of pages that have accordions.
  • Find all accordion buttons.
  • Activate each button.
  • Check for aria-expanded="true".
  • Check that accordion content becomes visible.
  • Check that focus stays on the button.
  • Fail based on any of the above.
Form errors
  • Go to a set of pages that have forms.
  • Leave the form blank and activate the submit button.
  • Find fields with errors.
  • Check for aria-invalid="true".
  • Check that error messages are present.
  • Check that error messages are associated with the fields.
  • Fail based on any of the above.
Modal dialogs
  • Go to a set of pages that have modal dialogs.
  • Find and activate the trigger button.
  • Check that focus moves inside the dialog.
  • Close the dialog using Escape.
  • Check that focus returns to the trigger.
  • Fail based on any of the above.

So, Playwright can navigate to a page and put it into the state you want to test.

It can then check the behaviour itself or run axe-core to check that state.

Feature 3. Running automatically

Any of these tests could be set to run automatically at different stages of development.

Method 1:

Developers could run tests against their local build whenever they save changes.

Method 2:

Tests could run automatically whenever code is pushed to a repository.

Method 3:

Tests could also run against a build on a regular schedule.

Feature 4. Blocking builds and releases

Quick side note:

Continuous Integration (CI) is a process where automated checks can run whenever developers make changes to code.

When a Playwright test fails, CI can be configured to stop a build or block a release.

Playwright can produce a report showing which tests failed.

Developers would need to resolve the failing tests before the build or release could proceed.

This can prevent known accessibility issues from reaching production.

Feature 5. More powerful reporting

Playwright can produce detailed HTML reports covering tests across multiple pages.

Playwright can run the same tests across Chromium, Firefox and WebKit.

How does it work?

Playwright tests are written in JavaScript.

Developers write JavaScript tests that tell Playwright what to do in a browser.

Here’s a simple example of a Playwright test that uses axe-core.

The test will:
  1. Go to the page
  2. Run axe-core
  3. Filter for the critical and serious issues
  4. Expect there to be none
Disclaimer:

This example has been simplified for teaching purposes. It's not intended to be a production-ready test.

// Imports left out to save space
test(
  'home page has no critical or serious issues',
  async ({ page }) => {
    await page.goto('https://example.com');
    const results = await new AxeBuilder({ page })
      .analyze();
    const important = results.violations.filter(
      v => v.impact === 'critical' ||
           v.impact === 'serious'
    );
    expect(important).toEqual([]);
  }
);

Developers save their tests in files with names such as:

accessibility.spec.js

Playwright automatically finds these test files.

Then they can run all the tests from the terminal with:

npx playwright test

They could also just run a single test by adding the test file name:

npx playwright test accessibility.spec.js

Weaknesses

Like any solution, Playwright has a range of weaknesses too.

Weakness 1: Advanced interaction tests are fragile

Different websites use different structures and approaches for the same components.

Tests that find, open and interact with components often need detailed knowledge of how they’re built.

Tests can fail when:
  • The markup doesn’t match what the test expects
  • The code, content or timing changes

That’s manageable in a closed, predictable world like a design system.

It’s much harder in large applications with many teams, different codebases and legacy systems.

Weakness 2. Tests only find what they’re told to look for

For example, a test might:
  • Find accordion triggers by their button role
  • Miss accordion triggers that don’t have that role

These cases don’t fail. They just aren’t tested.

So developers may think everything has passed.

Weakness 3. Tests can check the wrong thing

For example, a test might:
  • Activate an accordion button
  • Expect focus to move into the accordion content

But focus should stay on the button, and its aria-expanded state should change to true.

This means a test can pass while confirming incorrect accessibility behaviour.

Weakness 4. Passing tests don’t guarantee accessibility

Even hundreds of passing tests don’t guarantee an accessible experience.

We still need to ask questions such as:
  • Is this name meaningful?
  • Does this focus order make sense?
  • Is this page usable with a screen reader?

Best fit

So, where does Playwright work best for accessibility testing?

1. Excellent for regression testing

Once an issue is found and fixed, a test can keep checking that it stays fixed.

2. Great in controlled environments

Playwright is particularly useful in design systems, where components and their expected behaviours are known.

Wrapup

  • Playwright has powerful features.
  • It also has important weaknesses.
  • Really good in some situations.
  • It doesn’t replace manual testing or testing with people with disability.

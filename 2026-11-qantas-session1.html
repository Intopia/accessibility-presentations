Accessibility testing tools: Strengths and weaknesses

All of the accessibility testing tools we just reviewed have limitations.

How much can automated tools find? It depends how you count.

Counting by WCAG success criteria

Only around a quarter to a third of WCAG success criteria can be fully tested automatically. The rest need human judgement.

Source

Counting by issues found

A 2021 Deque study found automated tests caught 57% of issues on real sites, because the most common issues are the ones machines can detect.

Source

Either way, if an accessibility testing tool passes a website, this doesn’t necessarily mean the site is accessible.

Source

Not all automated testing is the same. There are three broad types.

1. Automated scanners

Tools like axe, WAVE and Lighthouse check the page against a set of rules, as it is when the scan runs.

Strength: fast, consistent and repeatable.
Weakness: they only see the page at rest, and can’t make judgement calls.

2. Scripted browser tests

Tools like Playwright and Cypress act like a user: pressing keys, opening menus and dialogs, then checking what happens.

Strength: can test behaviour, not just markup.
Weakness: someone has to decide what “correct” looks like, then write and maintain each test.

3. AI-assisted tools

Newer tools use AI to attempt judgement calls, such as whether alt text matches an image or link text makes sense.

Strength: can flag issues rule-based tools can’t.
Weakness: results can vary between runs, and can be confidently wrong.

Even with all three types, there are things tools still struggle with:

1. Meaningful use of content and context

Scanners can’t judge if headings, links or alt text make sense in context. AI tools can suggest problems, but their suggestions still need a human check.

2. Visible focus indicators

Tools can detect that a focus style exists, but rarely confirm it’s clearly visible or has enough contrast against its surroundings.

3. Logical reading and focus order

Scanners don’t assess order. Scripted tests can check tab order, but only against an order a person has decided is correct.

4. Keyboard use in complex components

Scanners can’t test how menus, dialogs or custom controls behave. Scripted tests can, but only for the behaviour someone has written a test for.

5. Target size and spacing

Tools can now measure targets against the 24 by 24 pixel minimum, but deciding whether an exception applies still needs judgement.

6. Error prevention and recovery

Tools can check that error messages exist and are linked to fields, but not whether they actually help users fix the problem.

7. Clear, understandable language

Readability tools can estimate reading level, but can’t judge whether content is clear for its intended audience.

8. Timing and animation issues

Tools don’t reliably detect timeouts, unexpected motion, or whether users can pause, stop or extend them.

9. Captions and transcripts

Tools can check that a caption track exists, but not whether captions or transcripts are accurate, complete or synchronised.

10. Authentic user experience for people with disability

No tool can show what it’s really like to use a site with a screen reader, voice control or switch access. That needs testing with people with disability.

However, these tools are still very useful, as long as we are aware of what each type can and can’t do.

axe-core and Playwright

axe-core

axe-core is an accessibility testing engine.

If you’ve used the axe DevTools browser extension, you’ve already used axe-core.

It’s the engine inside that extension, and inside many other accessibility tools, including Lighthouse.

axe-core runs inside the web page itself.

Page loads
↓
axe-core runs inside the page
↓
axe-core returns its results

That’s all any axe tool does.

The extension, the command line and Playwright all do these same three steps. They just show the results differently.

axe-core checks the page for many automatically detectable problems at once, such as:

  • Missing accessible names
  • Invalid ARIA
  • Colour contrast
  • Form labelling
  • Landmark and heading issues

Each problem is given an impact level:

  • Minor
  • Moderate
  • Serious
  • Critical

axe-core also reports things it can’t decide on its own.

These are called “incomplete” results, and need a person to check them. A common example is text over a background image.

But axe-core can only detect issues that can be determined automatically.

It can’t tell us:
  • Is the focus order logical?
  • Is a visible label meaningful?
  • Does the alt text describe the image?
  • Does it make sense with a screen reader?
  • Is the keyboard interaction right for this component?

So axe-core gives us automated accessibility testing, not a complete accessibility audit.

Playwright

Playwright is a browser automation and testing framework.

It can control a browser much like a person would.

Developers install it with a couple of commands. You don’t need to.

Playwright can:
  • Open a page and log in
  • Click buttons and complete forms
  • Open dialogs
  • Use keyboard commands
  • Wait for dynamic content
  • Take screenshots

This means Playwright can get an application into the exact state we want to test.

Open checkout page
↓
Add a product to the cart
↓
Open the cart dialog
↓
Run an accessibility test

Playwright and axe-core work well together.

axe-core can check a page, but it can’t navigate through an application.

Playwright does the navigating, then runs axe-core in the page it has opened.

There’s even an official package that connects the two:

@axe-core/playwright

But Playwright can also test accessibility on its own.

Playwright can check if elements have:
  • The expected accessible name?
  • The expected accessible description?
  • The expected role?
  • The expected error message connected to it?
  • Keyboard focus right now?

For example, Playwright can:

  1. Open the dialog
  2. Press Escape
  3. Check the dialog has closed
  4. Check focus went back to the button that opened it

This is functional accessibility testing: checking that things actually behave accessibly, not just that the code looks right to a scanner.

Reporting

On its own, axe-core just returns a list of results. It’s accurate, but raw.

Playwright gives us control over reporting, such as:

  • A readable report showing which tests passed and failed
  • Screenshots of the page when a test fails
  • Choosing which results matter, such as only serious and critical issues
  • Attaching the axe-core results to the report for later

Pass or fail

Development teams often run tests automatically, every time code changes.

This is called continuous integration, or CI.

Developer changes code
↓
Tests run automatically
↓
All tests pass?  →  Code can go live
Any test fails?  →  Code is blocked

Every Playwright test either passes or fails.

So a failing accessibility test can stop inaccessible code from reaching users.

Accessibility becomes a gate that code has to pass through.

And because it’s a gate, teams decide what fails the build.

For example, a team might fail the build on every axe-core violation, or only on serious and critical issues.

But notice: A person still has to decide what “correct” looks like.

Different variations

Measuring the importance of issues

Three concepts can be independently reviewed to determine the importance of accessibility issues.

  1. Impact on users
  2. Impact on the business
  3. Frequency

1. Impact on users

This defines how the issue impacts one or more types of users’ ability to accomplish a task.

A task could include:
  • Filling in a form.
  • Navigating to a location.
  • Accessing content.
  • Even choosing a date from a date picker.
Rating Explanation
Critical Stops one or more types of users from completing a task.
High

May cause serious problems or significant inconvenience to one or more types of users.

At least one method must be available that allows these users to complete the task, even if it requires additional time.
Moderate May cause problems or frustrations for one or more types of users.
Low May be an inconvenience or irritation to one or more types of users.

2. Impact on the business

This defines the impact on the business if the task can’t be completed.

Rating Explanation
High Will have a significant impact on the business.
Moderate May have an impact on the business.
Low Will have little to no impact on the business.

3. Frequency

This defines how often the issue occurs across the tested pages/processes.

Rating Explanation
High The issue occurs on almost all tested pages.
Moderate The issue occurs numerous times within tested pages.
Low The issue occurs rarely across tested pages.
